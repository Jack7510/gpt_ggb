# 显性设计要素

以下是本技能的文档约定，不是 ASD-STE100 的图表要求。
以实际实现或明确的拟议设计填充内容。不要把示例字段当作默认产品能力。

## 要素覆盖表

在完整文档中记录四类要素的章节位置、状态和依据。
状态可以是“已提供”“待确认”或“不适用”。后两种必须说明原因。
例如：无生命周期的纯函数可以没有状态机，但仍有输入输出契约。

## 架构图

- 画出范围内组件、外部依赖和责任边界。标记数据与控制方向。
- 区分同步调用、异步消息和持久化关系。不要仅画未注明含义的箭头。
- 涉及浏览器、服务器、凭据、模型输出或执行器时，显示信任边界和允许的数据方向。
- 图后用责任表说明组件拥有和消费的资源。明确状态、数据和错误处理的所有者。
- 只描述有证据支持的安全边界，不声称未知系统已满足安全属性。

## 流程图

- 指定入口、参与者、前置条件和结束结果。
- 画出正常路径和已定义的条件分支、拒绝、失败、超时或取消路径。
- 涉及重试时，记录触发条件、上限和终止行为；未定义时标为待确认。
- 涉及多个参与者时，可补充序列图以表达调用顺序；序列图不能掩盖缺失的分支条件。
- 标记外部副作用及其发生点。只有契约支持时才画补偿或回滚路径。

## 状态机

提供 `stateDiagram-v2` 图和迁移表。至少明确：

| 源状态 | 事件 | 守卫条件 | 动作及副作用 | 目标状态 | 状态所有者 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |

- 给出初始状态、终态及状态含义。终态有出边时说明为什么允许再次迁移。
- 定义非法迁移的处理方式。明确重复事件与并发迁移的处理规则（如果相关）。
- 区分任务状态、事件、步骤和 UI 展示，不能混用这些概念。
- 图和迁移表必须一致。没有持久生命周期的对象不需要虚构状态。

## 契约

每个范围内的接口、事件或持久化边界按需要记录：

| 项目 | 要说明的内容 |
| --- | --- |
| 标识与所有者 | 接口名、版本、提供方、消费方、证据路径 |
| 前置条件 | 调用条件、身份与权限要求 |
| 输入 | 字段名、类型、必填性、约束；区分缺失、null 和空值 |
| 输出 | 成功结果、类型及完成判据 |
| 不变量 | 调用前后必须成立的关系及状态限制 |
| 错误 | 稳定的错误码、触发条件、消费方处理行为 |
| 副作用 | 状态变化、写入、事件发布及原子性范围 |
| 时序 | 超时、取消、重试、幂等、顺序与并发语义（如果相关） |
| 演进 | 兼容性规则、版本变化与迁移影响（如果相关） |
| 验证 | 可观察的验收条件、对应测试或未验证事项 |

已有 schema、类型或协议是字段依据。说明文不能悄悄改变契约。
必要时给出最小成功和失败示例，使用占位数据，不使用凭据或真实用户数据。
未定义的行为写“待确认”，并说明影响；不以假值填表。

## 交叉检查

- 架构组件与流程参与者使用相同名称。
- 流程结果与状态机的目标状态一致。
- 状态机事件能定位到契约或内部触发依据。
- 契约的副作用在流程及责任归属中可见。
- 每条关键要求关联验收条件；没有实现依据的方案明确标为拟议设计。
- 图在目标输出中可读。箭头方向和标签不能依赖正文猜测。
