# STE 技术文档

使读者能确定：哪个主体在什么条件下执行什么动作，产生什么结果，失败时怎样处理。
同时用图、表和契约表达系统行为，不能只用散文描述设计。

## 范围与依据

- 保留用户指定的语言、格式、目的、路径和项目文档归属。默认沿用原文语言。
- 阅读项目的 AGENTS.md、相关权威文档、实现、调用方和测试。更新已有文档时，沿用其结构。
- 区分已实现行为、拟议设计和待确认事项。给出可定位的来源；不要把推测写成事实。
- 此技能授权文档工作，不授权修改业务代码、部署、迁移、调用真实服务或发布文档。
- 普通文字修订只更新受影响段落及其相关图表。完整设计文档必须覆盖下述显性要素。

## 文字约束

先阅读 [references/ste-writing.md](references/ste-writing.md)。

- 英文使用 ASD-STE100 写作规则和受控词汇。记录核对的版本及词汇依据。
- 中文使用相同的清晰写作原则，但不能称为 ASD-STE100 合规文本。不要自行翻译全文为英文。
- 一句话表达一个主要意思。明确主体、动作、对象、条件和结果。步骤用直接的指令。
- 同一概念使用同一术语。首次出现时解释缩写。保留准确的代码标识符、字段和接口名。
- 用可检查的要求替换“适当”“及时”“支持”“可靠”等模糊描述。依据不足时标注待确认，不编造数值。
- 明确区分“必须”“应当”“可以”，并在契约中固定其含义。不要因改写而改变要求强度。

## 显性要素

完整文档提供以下四类要素。先阅读
[references/explicit-elements.md](references/explicit-elements.md)，按文档范围选择粒度。
如果某类不适用，在覆盖表中写出具体原因；缺少证据应标记待确认，不能标为不适用。
对于局部修订，保留无关内容，不为满足此清单扩写整个文档。

| 要素 | 文档必须回答的问题 |
| --- | --- |
| 架构图 | 组件分别拥有什么责任？数据经过哪些边界？谁调用谁？信任边界在哪里？ |
| 流程图 | 什么触发流程？正常路径是什么？分支、失败和结束条件是什么？ |
| 状态机 | 有哪些合法状态？什么事件触发迁移？迁移需要什么条件？谁能修改状态？ |
| 契约 | 谁提供和消费接口？输入、输出、不变量、错误及兼容性规则是什么？ |

- Markdown 默认使用 Mermaid 架构图、流程图和 `stateDiagram-v2` 状态机。
- 架构图使用带边界分组的 `flowchart`；流程图显示实际执行顺序，不能只复制架构图。
- 图中名称、状态、事件和字段必须与正文、契约及实现一致。标明拟议的组件或路径。
- 图后说明关键关系和异常行为。图不能替代字段表、迁移表及规范性要求。
- 非 Mermaid 输出使用目标格式可承载的图形。不能渲染时保留可编辑图源并说明验证限制。

## 写作与检查

1. 确定读者、范围和依据。把已知信息与待确认信息分开。
2. 建立术语表及要素覆盖表。定位受影响的图、状态和接口。
3. 先对齐图、迁移表和契约，再写正文。原有模板无需改成固定章节顺序。
4. 检查每条要求能否通过输入、观察结果或测试判定。未知要求保留问题和影响。
5. 按 STE 参考检查文字，确保简化句子没有删除条件、否定、单位、错误或例外。
6. 交叉检查图文、状态迁移和契约：每条分支有结果，每个字段有来源，每个状态有合法迁移。
7. 使用已有的文档检查和图表渲染工具验证语法及可读性。无工具时做静态核对，不声称已渲染。

交付时简要说明修改位置、覆盖要素、验证结果和待确认事项。
只在确实核对了适用写作规则、词义、词性和技术词汇后声称符合 ASD-STE100。
仅做文字自检时，表述为“已应用 STE 原则；完整规则和词典核对未完成”。
